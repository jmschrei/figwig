Unreleased

Reading
-------

	- The ISA-L kernel knows the inflate state of ISA-L 2.32.1, which python-isal 1.9 bundles, as it knew 2.31.1's (python-isal 1.8), so ``engine='auto'`` reads with ISA-L under either, where python-isal 1.9 read with zlib. The two versions' ``struct inflate_state`` is the same, field by field.

	- ``oob=`` on ``BigWigReader.read`` and ``read_bigwig`` sets the value of bases past the end of a chromosome, as in pybigtools' ``values()``. The default stays NaN. Thanks @casblaauw!

	- A bigWig read with ISA-L gives its inflate kernel ISA-L's two functions in one tuple, where it gave them apart and numba typed each on every call under the GIL: a call of the kernel on an empty batch takes 2.9 µs, where it took 58.3 µs. On the benchmarks' server, 1,000 windows of 2,048 bp from the K562 ATAC-seq fold-change bigWig read in 9.4 ms on 8 threads, where they took 10.8 ms, and 20,000 windows in 103 ms on 32 threads, where they took 117 ms; 20,000 windows on 8 threads read in 106 ms, where they took 112, faster in only three of six pairs. The values are the same.

figwig files
------------

	- A figwig file keeps the tile sums and zoom levels of each group whose sums take at most 256 MB, where it kept none for any group once the whole file's took more, about 350 genome-wide tracks on hg38 at the default tile, however its tracks were grouped. ``add_file``, ``figwig merge`` and ``append=True`` keep the summary each group had, where they dropped every summary of a file that grew past that; ``figwig merge`` takes its zoom levels from the first file that keeps a summary, and ``FigWigReader.zooms`` from the first group that does. The writer holds the tile sums past 1 GB in a temporary file beside the output until it closes. The 384 genome-wide tracks of 64 MethBase2 samples in groups of two now keep every group's summary and six zoom levels, in a file 1.6% larger, written on 16 threads of the benchmarks' server in 396 s with 3.6 GB of memory at the peak, where the file without summaries took 374 s and 2.2 GB. Large groups of sparse tracks pay more, since a group's summary holds a sum per track for every tile that any of them touches: the K562 Hi-C map at 10 kb, one track per bin in groups of 1,024, now keeps its summaries in a file 6.8% larger, written in 2.52 s on one thread, where it took 0.97 s, and in 0.95 s on 8 threads, where it took 0.60 s, with 885 MB of memory at the peak on one thread, where it took 245 MB. Files that kept every summary are written to the same bytes where zlib compresses the summaries (see below). The format is unchanged: a file in which some groups keep a summary and others none is a version 1 file, which figwig 0.2.0 and the parser generated from the Kaitai Struct definition read, summaries included.

	- A figwig file's tile sums and zoom levels are compressed by libdeflate where it is installed and the writer's engine, as the chunks are, and by zlib otherwise, at level 6 either way. With libdeflate their bytes differ from those earlier versions wrote; every reader reads both, and the format is unchanged. Writing the 10,246 cells of the benchmarks page's 10x PBMC file in track order, one group each with 1.2 GB of tile sums before compression, takes 24.9 s on one thread of the benchmarks' server, where it took 58.5 s with zlib, and 8.8 s on 8 threads, where it took 12.2 s, in a file 0.4% smaller. The 90,543 Fiber-seq reads of the benchmarks page in track order, whose summaries hold a few tiles each, write in 2.4 s on one thread as with zlib, in a file 0.2% larger.

	- ``tile_sums`` keeps the tile sums it inflates, up to 1 GB, for later calls on the same reader, where it inflated a group's whole genome-wide summary on every call. On one thread of the benchmarks' server, a 10 Mb view of one sample's two count tracks in a figwig file of 64 MethBase2 samples takes 0.23 ms after the first, where it took 3.1 ms and read 1.0 MB of the file each time, and 0.33 ms when the 64 samples are one group, where it took 155 ms and read 49 MB. The standard benchmark's genome browser views drawn from tile sums take 0.65 to 0.84 times as long.

	- ``FigWigWriter`` and ``write_figwig`` accept ``summary_index=True`` (default ``False``), which writes an optional index that lets a reader decode the summary of one region without inflating a whole level, and ``FigWigReader`` uses it automatically for selected-chromosome ``tile_sums`` and exact integer ``sums``, reading only the requested ranges, with the same values and the same fallback to raw values. The format stays version 1, and readers that do not know the index read the file as before. On one thread of the benchmarks' server, over 64 integer tracks in position order, ``tile_sums`` of a chromosome that is 20 Mb of 300 takes 19 ms, where it took 225 ms, and four integer ``sums`` of 200 kb 23 ms, where they took 81 ms; the file is 1.9% larger, and ``tile_sums`` of the whole genome takes 280 ms, where it took 262. Reading the sums no longer loops over the chromosomes in Python, so with or without the index ``tile_sums`` over a file of 100,000 contigs takes 21 ms, where it took 49. See :ref:`regional-summaries` and :doc:`benchmarks`. Thanks @tuner!

	- ``sums`` over a track stored as runs, such as the coverage ``figwig bam2fw -c`` writes, only decodes the changes of value before each interval, adds a run of integers once rather than base by base, and takes the tiles an interval covers whole from the file's tile sums when the track holds integers whose sums those keep exactly. On one thread of the benchmarks' server, the coverage of ENCODE ATAC-seq BAM ENCFF877LRY sums over 78,733 gene bodies in 0.47 s, where it took 7.9 s, and over 100,548 peaks in 0.41 s, where it took 1.6 s; a fold-change track over the gene bodies in 1.55 s, where it took 6.8 s; 48 count tracks over the gene bodies in 6.8 s, where they took 14.4 s. The sums are the same to the bit.

	- ``write_sparse``, and so ``figwig reorder``, stores a tile as a dense or runs chunk when either takes fewer bytes than a sparse one, as ``write`` does. Reordering the ATAC-seq coverage file gives the same 79 MB of runs chunks, where it gave 119 MB of sparse chunks. Scattered entries, such as cells' cut sites, are stored as before: the 10,246-cell PBMC file is the same to the byte.

	- ``is_figwig(path)`` tells whether a path is a figwig file from the magic number in its first four bytes, without opening it as a reader, so that code taking either a figwig file or bigWigs can choose its reader: it is False for a bigWig, a missing path or a directory. Thanks @casblaauw!

	- ``write_sparse`` sorts its entries by a radix sort of one packed key per entry on the writer's threads, where a numpy sort of the keys ran on the calling thread; keys in a few runs, and on one thread keys out of order only near each other, as reads given in position order are, still go to numpy's merge sort, which takes them faster. It hands the threads a call's small batches of groups packed into tasks that join their own chunks and tile records, so that the calling thread writes each task in one call. The 382 million pixels of the 4DN K562 Hi-C map (4DNFI18UHVRO) at 10 kb, as one track per bin in bin coordinates with both triangles, take the writer 12.1 s on 8 threads of the benchmarks' server, where they took 48.3 s, and 59 s on one thread, where they took 81 s; its 466 million pixels at 5 kb take 19.2 s on 8 threads, where they took 69.0 s; and the 3,882 cells of the Nagano 2017 single-cell Hi-C experiment at 10 kb, one track per cell, take 15.1 s, where they took 27.6 s. The files are the same to the byte, and the writer holds less memory beside its input: 1.14 GB on 8 threads at 10 kb, where it held 1.32 GB.

	- A file in track order hands its tracks' blocks to the threads packed into tasks of a share of the entries each, where each track's blocks on each chromosome were a task of their own: the Nagano cells at 1 Mb take 49 s on 8 threads in track order, where they took 70 s, and ``figwig reorder`` writes the ATAC-seq coverage file in track order in 27 s, where it took 45 s, and in position order in 26 s, where it took 44 s. The files are the same to the byte.

	- A sparse read sorts its entries by a counting sort straight from its tasks' parts, cut among its threads, where it joined the parts and sorted them on the calling thread, and ``read_entries`` reads its chromosomes together while their plan holds at most about a million (tile, group) pairs or the longest chromosome's, where it read one chromosome at a time. The 38.6 million entries of chromosome 1 in the 10 kb Hi-C file read in 0.13 s on 8 threads, where they took 0.52 s; one cell's contacts over the genome in the Nagano file read in 1.9 s at 10 kb, where they took 3.1 s, and in 0.064 s at 1 Mb, where they took 0.41 s. The entries are the same, in the same order.

	- A read cuts a group's chunks into batches in a compiled loop where the group has more than 8 chunks in the read, where a Python loop stepped through every chunk, and a file opens checking its tracks' records a column at a time, where it checked them one by one: the 617,666 tracks of the 5 kb Hi-C file open in 0.45 s, where they took 0.53 s.

	- ``sums`` over tracks of several groups runs every group's batches at once on the threads, where it summed one group at a time, so that a file of many small groups summed on one thread whatever ``n_jobs`` was. A read of many small groups takes batches of up to 128 KB per thread of the whole read's chunks, where it cut every group's chunks into two batches per thread: 1,024 tracks in 128 groups on 32 threads were 4,505 batches of a chunk or two, and are now 128. On a read of several groups each thread takes the next batch as it finishes one, and a read takes no more than one thread per 256 KB of the chunks it decodes and per 2 MB of a dense output, and at least 4, since reads of a few hundred KB of chunks took longer on 16 or 32 threads than on 2 to 8. Numba's list of a kernel's compiled signatures, which a read asked for twice and which hashes every signature's types in Python, is no longer asked for. On the benchmarks' server, 1,024 tracks in groups of 8 over 20 Mb of chr1 sum over 4,096 intervals in 1.6 s on 8 threads, where they took 3.1 s, and in 0.44 s on 32, where they took 3.1 s; 128 windows of them read in 0.046 s on 32 threads, where they took 0.48 s; and a genome browser's views of 256 of them, from a base per pixel out to the whole region and back, take 0.62 s in all on 8 threads, where they took 3.9 s. The values are the same.

	- ``sums(..., paired=True)`` in position order sums its batches of tracks side by side on the reader's threads, one each, where each batch was a read spread over every thread: the 90,543 Fiber-seq reads of the benchmarks page, each over its own span, sum in 1.6 s on 8 threads and 2.0 s on 32, where they took 2.9 s. Batches of float tracks are still read one after another on every thread, since their float sums depend on the threads. A file's group indexes, summaries and zoom levels inflate through libdeflate where it is installed.

	- ``write(..., ends=)`` encodes intervals on the writer's threads, where it encoded every tile on the calling thread, so that a write of read depth as runs took as long on 32 threads as on one. Each tile's sums are kept and folded into the statistics in the order the calling thread folded them, so the file is the same to the byte. The read depth of a full HCT116 ATAC-seq BAM, written as runs, takes 3.4 s on 8 threads of the benchmarks' server, where it took 12.4 s, and 2.1 s on 32, where it took 12.3 s.

	- ``write_sparse`` packs a call's pieces of entries, a group on a chromosome each, into tasks of at least 65,536 entries, each encoded in one kernel call per buffer, where each piece was a task with its own encoder call, and keeps no tile sums for a file too wide to keep summaries, where each piece zeroed a (tiles, tracks) array that was never read. A file of many tracks also opens and closes checking and inferring its tracks an array at a time, where it went track by track in Python. The 4DN K562 Hi-C map at 10 kb, a track per bin, writes in 9.1 s on 32 threads of the benchmarks' server, where it took 11.2 s, and the 3,882 Nagano cells at 10 kb in 8.9 s, where they took 10.3 s; the large-tier PBMC cells write in 0.52 s on 8 threads, where they took 0.65 s, holding 153 MB beside their input, where they held 447 MB. The files are the same to the byte.

	- ``sums(..., paired=True)`` over integer tracks and intervals of a few tiles each reads every interval at once, each with its own track's chunks or blocks alone, where it read batches of up to 16 tracks over all their intervals: the 90,543 Fiber-seq reads of the benchmarks page, each over its own span, sum in 0.69 s on one thread, 0.15 s on 8 and 0.13 s on 32 in position order, where they took 2.8, 1.5 and 1.6 s, and in 0.36 s on 8 threads in track order, where they took 9.9 s. The sums are the same; a batch's error for a sum outside an integer output and ``nan='count'`` keep the batches.

	- A read with labels over several groups of integer tracks runs in bands of windows side by side on the threads, where it ran a group at a time, and sums of integer tracks below 2**24 go straight into a float32 output, where they went through a float64 copy of it: the sum of every Fiber-seq read over 8,192 windows takes 0.056 s on 8 threads, where it took 0.12 s, and 0.061 s on 32, where it took 0.81 s; ten pseudobulks of the 10,246 PBMC cells over 8,192 windows take 0.11 s on 8 threads, where they took 0.19 s, and hold 0.68 GB, where they held 2.0 GB.

	- A few long windows summed per bin, as a genome browser's views are, are read as parts of whole bins on the threads, where each was a task per group: a session of views over four dense conservation tracks takes 0.20 s on 8 threads, where it took 0.53 s, with the same values. A part's float sums can differ from those of one thread, and of a whole window on several threads, in rounding, since where windows overlap one read bins a chunk that four or more of them share from a scratch tile. A group's index is checked on its live tiles alone and its runs of chunks laid out at once, and the indexes a read needs load on up to 8 threads once one of them spans 131,072 tiles or more, where they loaded on the threads the read took: a reader's first view of six genome-wide count tracks takes 13 ms on 8 threads, where it took 22 ms, and of 256 tracks in 32 groups 7.7 ms, where it took 15 ms; a process running the count tracks' session peaks at 169 MB, where it peaked at 146 MB.

	- A track-order read plans every track's windows at once, and joins the tracks' block indexes as bytes, where it planned a track at a time: 16 PBMC cells over every chromosome read in 9.1 ms, where they took 15 ms, every Fiber-seq read's sparse values over 1,024 windows in 0.047 s on 8 threads, where they took 6.8 s, and the sum of every read over 8,192 windows in 0.089 s on one thread, where it took 15 s. A track-order writer encodes each task of tracks' blocks in one compiled call, of at most 2**18 entries, adds a call's pieces in one loop, and joins its block records as bytes at close: the Fiber-seq reads write in track order in 1.5 s on 1, 8 or 32 threads, where they took 3.9, 5.6 and 5.7 s, and the 10,246 PBMC cells in 5.9 s on 8 threads, where they took 18.1 s.

	- ``write_sparse`` checks the ranges of declared integer dtypes in one compiled pass, where it took each track's minimum and maximum with numpy, and checksums use libdeflate's crc32, 19 to 46 GB/s, where a table kernel ran at 2.4 to 2.8 GB/s: the full PBMC cells write in 7.7 s on 8 threads, where they took 12.2 s, and 4.5 s on 32, where they took 9.7 s. The files are the same to the byte.

	- ``write_sparse`` sorts its entries in fewer radix passes, starting above a tile's offset bits where a call's positions ascend, and on one thread sends keys out of order only near each other to numpy's merge sort only while at most one in 64 descends or the call has fewer than 16,384 entries, so that a single-cell contact map's calls, whose cells interleave within each tile, take the radix sort, at 9.1 ns an entry where the merge sort took 22. Its passes over a call's entries, the checks of positions, track ids, int64 ranges, infinity and declared dtypes, run in parts on the writer's threads, its int64 inputs are no longer copied, and a packed task's statistics fold in one call. The 4DN K562 Hi-C map at 10 kb, a track per bin, writes in 51 s on one thread of the benchmarks' server, where it took 58 s, and in 8.9 s on 8 threads, where it took 11.9 s; the 3,882 Nagano cells at 10 kb in 80 s on one thread, where they took 90 s, and in 13.2 s on 8, where they took 14.4 s, the fastest of 4 to 14 paired runs. On 32 threads, in the same pairs on a busier server than the timings above, the map writes in 6.8 s, where it took 13.1 s, and the cells in 6.6 s, where they took 9.9 s. The files are the same to the byte, and the writer holds less beside its input: 711 MB on one thread for the map, where it held 968 MB, and 625 MB for the cells, where it held 789 MB.

	- A read of fewer than one in 16 of a group's tracks, as one cell's of a single-cell file is, checks only those tracks' offsets in a chunk and passes over the chunks in which none of them has a base, where it checked every track's and decoded every chunk; reads of more tracks run as before. Where libc's ``pread`` and libdeflate both load, as everywhere but Windows, a batch is read, checked and inflated in one compiled call that holds no GIL, where each thread took the GIL between numpy calls and compiled ones; a read's planner finds every batch's arrays once per group, where it made some twenty numpy calls per batch on the calling thread; and an array of track indices is checked at once, where its items were checked one by one. On the benchmarks' server, one cell's contacts over the genome in the Nagano single-cell Hi-C file at 10 kb read in 8.5 s on one thread, where they took 12.8 s, in 1.23 s on 8 threads, where they took 1.97 s, and in 0.75 s on 32, where they took 1.45 s; 16 cells in 1.54 s on 8 threads, where they took 2.22 s; and 50 rows of the 10 kb Hi-C map, each a bin's contacts over the genome, in 0.15 s on 32 threads, where they took 0.24 s. The entries and values of these reads are the same.

	- A sparse read lists its entries' rows, channels and offsets as int32 while a window is narrower than 2**31 bases, and widens them to int64 as it gathers them, where it listed them as int64: chromosome 1's cis matrix of the 10 kb Hi-C map, read with ``sparse=True`` on one thread, adds 1.92 GB to its process at its peak, where it added 2.41 GB, and takes 0.52 s, where it took 0.58 s. The entries are the same, in the same order.

	- A ``write`` of windows on threads checks its values for infinity and against declared integer types in parts on the writer's threads, the latter in one compiled pass where it went through numpy a track at a time, and copies each group's block once, every group's of a call in one pass on the pool, where it copied a group's channels twice on the calling thread. The copies go in waves of at most 4 MB per thread, the next copied once the tiles of all but the last are encoded, so that a call holds two waves of copies at most, and the calling thread takes a part itself while the writer's threads are busy, they taking the next as they come free. On the benchmarks' server, 256 tracks over 20 Mb of chr1 write in 1.98 s on 32 threads, where they took 6.6 s, in 3.2 s on 8, where they took 6.3 s, and in 16.9 s on one, where they took 18.9 s; 1,024 tracks write in 10.4 s on 32 threads, where they took 21.1 s. The files are the same to the byte. On 32 threads the waves hold up to about 150 MB more than the calling thread's copies did: 2.01 GB at the 256 tracks' peak, where it was 1.86 GB.

	- A write's chunks are compressed by libdeflate and checksummed in one compiled call that holds no GIL, where the calling thread's numpy calls let it go and took it back three times a batch, and ``write_sparse`` plans and encodes each task of entries in two such calls, where it made some fifty numpy calls a task. ``write_sparse`` takes entries already in the writer's order without sorting them, and tests each piece of a call against the order rules before calling the check that raises. A writer with threads writes its chunks and blocks to the file in order on a thread of its own, with at most 64 MB queued for it, where the calling thread wrote them between batches. On 32 threads of the benchmarks' server, the 4DN K562 Hi-C map at 10 kb writes in 5.2 s, where it took 5.9 s, the Nagano cells at 10 kb in 5.8 s, where they took 6.6 s, and the 10,246 PBMC cells in 3.05 s, where they took 3.41 s, and in track order in 4.7 s, where they took 5.6 s, in 3.2 s on 8 threads, where they took 5.4 s, and in 7.7 s on one, where they took 9.3 s. The files are the same to the byte.

	- A first call compiles fewer copies of the kernels. Alone in a new process with an empty numba cache, on the benchmarks' server, ``read_entries`` compiles for 20 s, where it took 69 s, a dense read for 21 s, where it took 38 s, a sparse read for 22 s, where it took 40 s, and a track-order read for 3.6 s, where it took 7.9 s; a process that reads and writes every way compiles for 87 s, where it took 132 s. 	- A writer of many tracks looks each distinct dtype up once and sets its groups up in arrays, where it went through them in Python: a writer of the 90,543 Fiber-seq reads opens in 0.060 s, where it took 0.151 s, and in track order in 0.139 s, where it took 0.362 s. Converters and commands
-----------------------

	- ``figwig install-skill`` over an installed copy without ``--force`` prints the message saying to use it and exits with status 1, where it printed a traceback.

	- ``figwig bam2bw -c -r`` and ``figwig bam2fw -c -r`` divide by the reads, one for each read whose first aligned block starts inside its chromosome, as ``-r`` without ``-c`` and deepTools' CPM count them, where they divided by the aligned blocks, so that a read cut by a deletion or a skipped intron counted once per block: a K562 polyA RNA-seq BAM of 31.5 million mapped reads was divided by 42.6 million, and the 2.4 GB ATAC-seq BAM by 45.9 million for its 44.8 million. Outputs without ``-r`` are the same to the byte, and so is ``-c -r`` where every read is one block: no deletion or skipped intron, nor, in a SAM file or another file read by pysam's loop, an insertion.

	- ``--summary-index`` on ``figwig bw2fw`` and ``bam2fw`` writes the regional summary index, and ``figwig reorder`` and ``merge`` write one when the header of their input (of the first file, for ``merge``) announces one, unless ``--no-summary-index``, or when ``--summary-index`` is given.

	- ``figwig info -b`` counts a file's regional summary index apart from its unused bytes.

	- ``figwig bam2fw -c`` on threads writes each 4 Mb of a chromosome's coverage as one dense window, whose tiles the writer encodes on its threads, where it encoded every run on the calling thread, unless the 4 Mb hold fewer runs than one per 1,024 bases, as sparse coverage such as RNA-seq's does, which goes in as runs as before: the 2.4 GB ATAC-seq BAM takes 7.2 s on 8 threads, where it took 14.2 s. The file is the same to the byte, and one thread writes it as before.

	- ``figwig bam2bw -c`` and ``figwig bam2fw -c`` read a coordinate-sorted BAM file with a ``.bai`` no older than it a region at a time on every core, from the index's offset for each region's first base, and write each chromosome while the next is read, rather than keeping two events per aligned block of every read until the file ends. They do so at ``-p 8`` or more, for ``bam2bw`` from 128 MiB and 5 million mapped reads in its files, for ``bam2fw`` from 128 MiB and 50,000 mapped reads in each file; below these, set from timings on 25 BAMs of the test-data collection with a margin on the whole-file reader's side, and for a file the region reader cannot read exactly as the whole-file reader would, the whole-file reader runs as before. The 2.4 GB ATAC-seq BAM takes 1.6 s with ``bam2bw -c -u -p 8``, where it took 2.5 s, and 1.05 s at ``-p 32``, where it took 2.5 s; 4.9 s with ``bam2fw -c -u -p 8``, where it took 7.2 s, and 2.3 s at ``-p 32``, where it took 7.1 s. At ``-p 8`` the peak memory falls from 2.0 to 0.54 GB (``bam2bw``) and from 1.9 to 0.63 GB (``bam2fw``); at ``-p 32`` it is the regions in flight, 2.4 GB against 2.0 GB for ``bam2bw``. The bigWigs and unstranded figwig files are the same to the byte; a stranded figwig file holds the same values and the same bytes of chunks, the two strands' interleaved, so its index holds more runs: 0.14% more bytes in all on 8 million ChIP-seq reads.

	- ``figwig bam2fw --barcode-column`` no longer loses the counts of the last chromosome when the sizes file has 2, 4, 8, 16, ... chromosomes. The last cut between chromosomes, ``n << shift``, was 2**63 and wrapped to a negative number in int64, so that chromosome's keys were never decoded, with no error or warning: 32 chromosomes with one fragment on each wrote a file whose chr32 read as all zero. Files written before with such a count are missing that chromosome and have to be written again; for other counts the cuts are the same as before, and the files of 3, 5, 7 and 24 chromosomes are the same to the byte. Thanks @martinappberg!

	- ``figwig bam2fw -c`` of a BAM the region reader does not take, as one below 128 MiB is, writes its runs on the writer's threads (above): the collection's 50 MB K562 ATAC-seq BAM takes 1.2 s at ``-p 8``, where it took 3.5 s.

	- ``figwig fw2bw`` reads the next piece of a group while the bigWig writers take the last, where reading and writing alternated, and the bigWig writer lays out a window's items without a branch per base: twelve bigWigs (ATAC-seq and DNase-seq cut counts, and PRO-cap, PRO-seq, csRNA-seq, TT-seq and NET-seq per strand) convert from their figwig file in 44 s on one thread, where they took 67 s, and in 10.3 s at ``-p 8``, where they took 17.8 s. ``figwig bw2fw`` checks the values for infinity in one compiled pass, and bigWig reads keep one thread pool between reads, where each read started its own: the same twelve bigWigs convert in 52 s on one thread, where they took 59 s, and in 10.5 s at ``-p 16``, where they took 13.4 s. The files are the same to the byte.

	- ``figwig fw2bw`` writes the bigWigs of a group of at most ``-p`` tracks each on a thread of its own, with at most two pieces of the group in flight, where every piece waited for each of its tracks' bigWigs before the next was written; a larger group's bigWigs are written ``-p`` at a time, each piece whole before the next is read, as before: the twelve bigWigs above convert in 8.95 s at ``-p 8``, where they took 9.99 s, and in 9.1 s at ``-p 32``, where they took 10.1 s. With the writer's changes above, ``figwig bw2fw`` converts them in 9.3 s at ``-p 8``, where it took 10.4 s, and in 10.7 s at ``-p 32``, where it took 14.0 s. The files are the same to the byte.

	- ``figwig reorder`` into track order hands the writer each chromosome's entries as already sorted, and the track-order writer sums its blocks' tiles in one pass: the read depth of the HCT116 ATAC-seq BAM reorders in 39 s on one thread, where it took 57 s, at a peak of 7.9 GB, where it took 14.0 GB. The file is the same to the byte.

	- ``figwig bam2bw -c`` and ``figwig bam2fw -c`` take a SAM file's reads, and those of a BAM file the record kernel hands to pysam, in the kernel's blocks: a run of M, = and X operations split only at D and N, where pysam's ``get_blocks()`` began a block at every operation. An insertion, or a change between = and X, no longer splits a bigWig interval there, so a SAM gives the bigWigs of the same reads as a BAM to the byte; and ``-ps``/``-ns`` empty a read they reach across whole, where they emptied only its first or last operation and left the others covered, in bigWigs and figwig files alike. Without shifts, ``bam2fw -c`` already wrote the same figwig files, which keep values rather than intervals.

Documentation
-------------

	- The bundled Claude Code skill has a reference for Hi-C contact matrices, ``references/hi-c.md``: one track per bin with chromosomes measured in bins, since in bp a tile stops at 65,536 bases and a bp file took twice the bytes; both triangles and a ``diagonal`` track, so that ``labels=`` over rows and ``bins=`` over columns read a coarser resolution in one call with the diagonal counted once, as cooler counts it, where summing both triangles counts it twice; writing cooler's row-major pixels by the column's chromosome, after summing the pixels published ``.mcool`` files repeat, which ``write_sparse`` refuses; single-cell layouts; and the limits Hi-C sizes reach (``tile_sums``, track counts, a pseudo-chromosome's length). Version 0.2.0
=============

figwig 0.2.0 adds the figwig file format: any number of tracks over one genome in one file, read in windows from any subset of them, with converters from bigWigs and BAMs and a Claude Code skill that covers it; and faster bigWig reading and writing. The bigWig API only gains keywords, and files written by 0.1.0 read as before.

figwig files
------------

	- A new file format, the figwig file (``.fw``), holds the per-base values of any number of tracks over one genome in one file, with a JSON record of attributes per track and the name of the genome, and is read many windows at a time from any subset of its tracks into one ``(windows, tracks, width)`` array in the tracks' own dtype. ``FigWigReader``, ``read_figwig``, ``FigWigWriter`` and ``write_figwig`` mirror the bigWig API with a ``tracks=`` argument; ``select(**attributes)`` gives the tracks whose records match, ``stats`` each track's sum, nonzero bases, minimum and maximum over its nonzero bases. Version 1 of the format is specified and frozen on the format page, with a reference reader written from the page alone and a Kaitai Struct definition in the repository; a reader refuses a file of a later version, or one with a required feature it does not know.

	- Layout. Every track lies on a grid of ``tile`` bases, and the tiles of a group of tracks are one chunk, stored as nothing, dense, sparse, runs or a per-tile matrix, whichever is smallest, in the narrowest element type that holds the values exactly, compressed with zlib or libdeflate on ``n_jobs`` threads (``level=0`` keeps chunks raw). The index holds only the tiles with values, so a file of 100,000 single-track groups opens in a tenth of a second. ``order='tracks'`` stores each track's nonzero bases in blocks per chromosome instead, for reading a few tracks over the genome, and ``figwig reorder`` rewrites a file in the other order.

	- Reads. ``read(..., sparse=True)`` returns the nonzero bases as entries, ``labels=`` sums the tracks per label, which turns cells into pseudobulks, ``bins=`` sums each window per bin, ``read_entries`` returns every nonzero base of tracks over chromosomes, and ``channels=``/``items=`` arrange the tracks read by two attributes. ``sums(chroms, starts, ends, nan=, paired=)`` sums intervals of any lengths, with NaN bases propagated, skipped or counted. ``tile_sums`` gives each track's sum per tile from the file's summaries, and ``tile_sums(level=k)`` the zoom levels a file written with ``zooms=`` keeps, without decoding a chunk. A dense read whose output would pass 8 GiB raises instead of allocating it.

	- Writes. ``write`` takes windows or intervals of whole groups and ``write_sparse`` nonzero bases as entries, both encoded and compressed on the ``n_jobs`` threads. A track's dtype is declared or inferred; a float32 track keeps float32's rounding, and a value beyond float32, a 64-bit integer beyond 2**53 or an infinite value is refused before anything is written. The file is written beside its path and moved there at ``close``, so a failed write leaves the path as it was. ``append=True`` adds tracks to a file in place under its lock, and ``add_file`` and ``figwig merge`` copy the tracks of files written with the same chromosomes, tile, level and order.

	- Integrity. Every chunk carries a CRC-32 that ``verify=True`` checks, the header, tables and index records carry CRC-32s checked at open, and every count and pointer is bounded against the file before its bytes are read, so a damaged, crafted or truncated file raises ``ValueError`` rather than crashing. A reader checks on every read that the file at its path is the one it opened.

	- ``device="cuda"`` on ``read``, ``sums`` and ``read_figwig`` lands the output in GPU memory as a ``cupy.ndarray``, which PyTorch, JAX and TensorFlow take without a copy through DLPack; the new ``cuda`` extra adds cupy.

	- Dense float tracks, such as conservation or fold change, read 3 to 6 times faster and write up to twice as fast on many threads: three chr22 conservation tracks, 8,192 windows of 2,048 bp, read in 0.50, 0.07 and 0.03 s on 1, 8 and 32 threads of the benchmarks' server, against 0.80, 0.12 and 0.11 s from their bigWigs.

	- A first call compiles a quarter fewer kernel specializations, since the kernels pass constants to each other as plain values rather than literals that numba compiled a copy per value for: about 85 s for a process that reads and writes every way, where it was 116 s.

Converters and commands
-----------------------

	- ``figwig bw2fw`` writes bigWigs as the tracks of one figwig file, named and given attributes by a metadata table, with ``--missing nan`` for tracks whose zeros are measurements, ``--append`` and ``-z`` zoom levels; ``figwig fw2bw`` writes a file's tracks back as bigWigs with such a table; ``figwig bam2fw`` takes what ``figwig bam2bw`` takes and writes each input file as its own stranded pair of tracks, or with ``--barcode-column N`` a fragments file as one track per cell, ``--cells`` listing the cells to keep with their attributes: the 257.6 million fragments of the 10x PBMC experiment become its 10,246 called cells in 9 s on 8 threads of the benchmarks' server. ``figwig merge`` and ``figwig info`` complete the set. Every command refuses to write over an existing output without ``-f``, writes beside its path and moves the output into place when complete, and prints a message rather than a traceback for an input that is missing, not a BAM or cut short.

	- ``-c/--coverage`` on ``figwig bam2bw`` and ``figwig bam2fw`` counts every aligned base of each read (the CIGAR's M, = and X runs, as pysam's ``get_blocks()`` and deepTools' ``bamCoverage`` count them), or every base of each BED/tsv interval, in place of one end, with ``-ps``/``-ns`` moving a read's first base and its end and ``-r`` dividing by the reads; ``bam2fw -c`` writes the coverage as runs, each track its own group. On the 2.4 GB ATAC-seq BAM and ten more experiments the bigWig holds the same value at every base as ``bamCoverage --binSize 1``, 3 to 8 times faster; the 2.4 GB BAM takes 3.4 s on 8 threads of the benchmarks' server against deepTools' 14.9 s.

	- ``figwig bam2fw`` and ``figwig bam2bw`` check each BAM's header against the sizes before reading: a shared chromosome of another length, or no shared chromosome, is refused by ``bam2fw`` and reported on stderr by ``bam2bw``, which goes on as bam2bw 0.5.1 does; an hg19 BAM against hg38 sizes converted silently before. ``figwig bw2fw -s`` refuses a sizes file that shares no chromosome with a bigWig, where it wrote a file of zeros. An empty track survives the round trip through ``fw2bw`` and ``bw2fw``: ``BigWigReader`` opens a bigWig without a data index, which it refused as unreadable.

Reading
-------

	- The bigWig reader takes a file whose index leaves lie in natural chromosome order (chr1, chr2, ..., chr10), which it refused as unsorted where pyBigWig read it. ``keep_nan=`` on ``BigWigReader.read`` and ``read_bigwig`` reads an interval whose value is NaN as NaN rather than ``missing``.

	- ``engine='auto'``, ``'zlib'`` or ``'isal'`` on ``read`` and ``read_bigwig``: with python-isal 1.8 built on ISA-L 2.31.1 installed (the new ``isal`` extra, which the ``bam2bw`` extra includes), data blocks inflate through ISA-L from the numba kernel without the GIL, 1.3 to 1.5 times faster on the benchmarks' bigWigs on 1 to 8 threads; every engine gives the same values. Thanks @YaoxiangLi!

Writing
-------

	- The kernel that summarizes items into a zoom level holds its open record in locals, so levels summarized on different threads no longer share a cache line, which made the kernel many times slower in some processes. The files written are unchanged. Thanks @YaoxiangLi!

	- With threads, ``BigWigWriter`` plans, encodes and summarizes each batch on threads of its own, so the calling thread only takes the next call's values, and sorted, valid input is confirmed in one compiled pass. The files written are unchanged byte for byte; writing the benchmarks' tracks with libdeflate and no zoom levels on 8 threads takes 1.4 to 1.5 times less. Thanks @YaoxiangLi!

Version 0.1.0
=============

Reading
-------

	- Initial release. ``BigWigReader(path).read(chroms, starts, width, out=None, n_jobs=8, missing=0.0)`` reads the per-base values of many windows of one width into a float32 numpy array of shape ``(n, width)``, on up to ``n_jobs`` threads, or one per CPU with ``n_jobs=-1``. ``read_bigwig`` does the same in one call, and given a list of bigWigs reads them all into one array of shape ``(n, len(bigwigs), width)``, with every file's batches on one pool of threads.

	- The values are those pybigtools' ``values(chrom, start, end, missing=missing)`` gives: ``missing``, 0 unless given, where no interval covers a base or an interval's value is NaN, and NaN past the end of a chromosome. A window on a chromosome that the file does not have, which writers leave out when it has no data, is ``missing`` throughout, and a warning names the chromosomes.

	- bedGraph, varStep and fixedStep sections are read, compressed or not, including pyBigWig's fixedStep blocks whose index entries overlap by a few bases. A file or data block that figwig does not read, such as a bigBed, a big-endian bigWig, a corrupt or truncated index, or a block with overlapping intervals, raises a ``ValueError`` that says what it found.

	- A ``BigWigReader`` can be read from several threads at once and pickled, so it can be part of a PyTorch Dataset read by DataLoader workers under any start method.

	- The reader began inside tangermeme's ``extract_loci`` (tangermeme #107).

Writing
-------

	- ``write_bigwig(paths, chrom_sizes, chroms, starts, values, ends=None, missing=0.0)`` writes what ``read_bigwig`` reads: windows on any chromosomes, in any order, with values of shape ``(n, width)`` for one file, or ``(n, len(paths), width)`` for several, channel ``i`` to the ``i``-th file. With ``ends``, it writes intervals and one value for each. Bases and intervals whose value is ``missing`` or NaN are left out, so that reading with the same ``missing`` gives the values back, and bases past the end of a chromosome, which ``read_bigwig`` gives as NaN, are accepted there. ``BigWigWriter(path, chrom_sizes, zooms=10, level=6, engine='auto', n_jobs=8)`` writes the same values a batch at a time with ``write(chroms, starts, values, ends=None, missing=0.0)``, each call after the last. Values are converted and laid out about a million at a time, however many one call holds. Data blocks are compressed on up to ``n_jobs`` threads by zlib's ``compress2()``, or by libdeflate when the ``deflate`` package is installed (the new ``fast`` extra), both called without the GIL, except on Windows, where neither library can be loaded and Python's zlib module compresses the blocks; ``engine='isal'`` uses ISA-L. Zoom levels are built when the writer is closed.

	- Each window, or each 65,536 bases of a wider one, is written as whichever section type takes it in the fewest bytes: fixedStep for runs of bases, varStep for scattered bases, or bedGraph for stretches of one value. Intervals are written as bedGraph, as they are given.

	- Written files are laid out as libBigWig, pyBigWig's writer, lays them out, and a file of intervals, or of single bases as windows of width 1, written with ``missing=numpy.nan``, without zoom levels and with zlib at level 6, is pyBigWig's byte for byte. Where libBigWig writes a wrong value, figwig writes the correct one: the header's maximum when the first value is the largest or no value is positive, the end of the last fixedStep block of each call, which libBigWig puts 6 bases past it, and the sum and sum of squares of the last zoom record of each zoom block, which libBigWig leaves at 0. libBigWig's empty blocks are not written, and zoom levels go on past a level that is no smaller than the one before it, where libBigWig stops.

figwig bam2bw
-------------

	- ``figwig bam2bw``, a command, is bam2bw 0.5.1 with the same arguments, outputs and messages, reading files as the winner of a speed search over bam2bw's code reads them, a BAM file with libdeflate and a numba kernel on the ``-p`` threads and a BED/tsv file with a numba kernel, and writing the counts with ``BigWigWriter``, with libdeflate at level 1. Its bigWigs hold bam2bw's entries, but not its bytes, and ``-z`` writes figwig's zoom levels. ``-p`` is a number of cores: files are read one after another, each on every core, and files read on one thread (SAM, ``--mate_pairs``, remote files, gzipped BED/tsv files that are not BGZF) by a pool of processes alongside them. It needs the new ``bam2bw`` extra. A BAM file's keys, one per counted read end, are counted a group of chromosomes at a time while the file is read and then dropped, so that for a coordinate-sorted BAM the array that holds them is the size of its largest chromosome's rather than the whole file's.

Claude Code skill
-----------------

	- ``figwig install-skill`` installs figwig's Claude Code skill, which teaches a coding agent to read and write bigWigs with figwig and to convert reads with ``figwig bam2bw``: the signatures and shapes, the rules a write follows, the error messages and their causes, and the measured gain from threads. It copies the skill into ``~/.claude/skills/figwig``, or ``-d DIRECTORY/figwig``; ``--symlink`` links to the package's copy instead, and ``--force`` replaces an installed copy, which an upgrade of figwig needs to pick up a changed skill.

Platforms
---------

	- Tested on Linux with Python 3.10 to 3.14, and on macOS and Windows with Python 3.10 and 3.13. On Windows, which has no ``os.pread`` and where neither zlib's library nor libdeflate's functions can be loaded, blocks are read by seeking the file, and decompressed and compressed by Python's zlib module, with the same values. ``figwig bam2bw`` runs on Linux and macOS, since pysam does not support Windows.
