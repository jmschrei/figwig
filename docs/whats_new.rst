figwig files
------------

	- A new file format, the figwig file, holds the per-base values of any number of tracks over one genome, with a JSON record of attributes for each track and the name or URL of the reference genome, and is read many windows at a time from any subset of its tracks into one array of shape ``(windows, tracks, width)``, in the integers the tracks were written as. ``FigWigReader(path).read(chroms, starts, width, tracks=None, out=None, dtype=None, n_jobs=8)``, ``read_figwig``, ``FigWigWriter(path, chrom_sizes, tracks, genome=None, attributes=None, tile=16384, groups=8, level=6, engine='auto', n_jobs=8)`` with ``write(chroms, starts, values, ends=None, tracks=None)``, and ``write_figwig`` mirror the bigWig API; ``FigWigReader.select(**attributes)`` gives the indices of the tracks whose records match, and ``FigWigReader.stats`` each track's sum, nonzero bases, minimum and maximum. Every track lies on one grid of tiles, so a window's tiles are found by division; the tiles of a group of tracks are one chunk, stored as nothing when every value is zero, and otherwise densely or as nonzero bases in the narrowest integer type that holds them, compressed with zlib or libdeflate on ``n_jobs`` threads. Six genome-wide count tracks that take 971 MB as bigWigs take 225 MB as one figwig file; reading 8,192 windows of 2,114 bp from the file took 0.130 s on one thread and 0.051 s on 8, against 0.907 s and 0.170 s from the six bigWigs with ``read_bigwig``, and 32 batches of 64 windows on one thread took 0.043 s against 0.544 s. The benchmarks page has the numbers for 1 to 96 tracks and 1 to 32 threads, and for the conversions.

	- A figwig file is written in one of two orders, ``order='positions'`` (``'csc'``), the tile layout for reading windows across many tracks, or ``order='tracks'`` (``'csr'``), which stores each track's nonzero bases in blocks per chromosome for reading a few tracks over the genome, and ``figwig reorder`` rewrites a file in the other order. ``FigWigWriter.write_sparse(chroms, positions, tracks, values)`` writes nonzero bases as entries, the form of single-cell cut sites and of a sparse matrix's triplets, and in an uncompressed position-order file a tile whose few tracks have values is stored as a matrix chunk, whose size grows with the values rather than with the tracks. ``read(..., sparse=True)`` returns the nonzero bases as a ``SparseWindows`` of entries, ``read(..., labels=)`` returns the tracks summed per label, which turns cells into pseudobulks in the read, ``read_entries(tracks, chroms)`` returns every nonzero base of tracks over chromosomes, and a dense read whose output would pass 8 GiB raises instead of allocating it. On the 10,246 cells of a 10x PBMC ATAC-seq experiment, 488 million cut sites in one uncompressed group, 512 windows of 2,114 bp summed into 10 pseudobulks took 0.08 s on one thread against 0.92 s from groups of 64 cells, and the genome-wide cuts of 20 cells took 0.12 s from a file in track order against 0.85 s from position order; the benchmarks page has the tables.

	- ``figwig bw2fw`` writes bigWigs as the tracks of one figwig file, named after their files or by a metadata table whose other columns become the tracks' attributes; ``figwig fw2bw`` writes a figwig file's tracks back as bigWigs with such a table, so the two round-trip names and attributes; and ``figwig bam2fw`` takes what ``figwig bam2bw`` takes and writes each input file as its own pair of stranded tracks, or one unstranded track, into one figwig file. A bigWig's values read from the figwig file exactly as ``read_bigwig`` gives them with ``missing=0.0``.

	- The format's second version, after a battle test of the first: the chunks, the index, the writer's guards and the reader's. A chunk's kind byte holds its kind in three bits, its element code in four and a stored bit. A *runs* chunk stores the bases where a track's value changes and the value from each on, so a track of 5 kb bins or a fold-change track, whose tiles took up to 80 times a bigWig's bytes as dense per-base values, takes a few dozen bytes per tile. A *float64* element type keeps an integer above 2**24 exact in a chunk that also holds a fraction, so a uint32 track grouped with a float track is no longer rounded; ``float64`` is a track dtype, and an integer beyond uint32 is inferred float64 rather than rounded through float32. A chunk that deflate would grow is stored as it is. The index holds only the tiles with values, deflated, so a group costs bytes for its data rather than 1.7 MB per genome, and the reader keeps 17 bytes per tile, as the docs said and the code did not; a pickled reader carries no index, and a file of 100,000 single-track groups opens in a tenth of a second rather than two seconds. Matrix chunks are allowed in compressed files where the sparse chunk's per-track counts would not deflate to less, so 100,000 cells in one compressed group write within a bounded buffer. ``read(..., bins=)`` sums each window per bin of bases, without laying the bases out, and ``bins=width`` gives each window's total per track. A version 1 file is refused with a message that says so.

	- Writer guards. A group listed in another order than the file's tracks had its values read back under the wrong names; a group's tracks now lie in the file's order within its chunks. A ``write_sparse`` call refused for a tile that ``write`` left open had already written part of the call and left the file unreadable; it now writes nothing. The file is written beside its path and moved there at ``close``, so a failed write, a writer never closed, or a conversion over its own input (``figwig reorder x.fw x.fw``, which emptied the input) leaves the path as it was; a writer garbage collected with values written and no ``close`` warns. A float32 track keeps float32's rounding of its values, so the statistics table describes what the file holds; a value beyond float32 raises unless the track is float64; a value too small for float32 is not counted as nonzero; -0.0 is 0; the sum statistic is compensated, so it does not depend on how the values were split between calls. NaN attributes are refused as not JSON, chromosome names over 65,535 bytes and genomes of more than 2**26 tiles are refused when the writer is made, and track order rejects a window that overlaps an earlier call's, as position order did.

	- Reader guards. Every count in the header and the index is checked against the file before its bytes are asked for, so a crafted ``metadata_length`` or ``n_runs`` raises a ``ValueError`` rather than a ``MemoryError``; chromosome lengths above 2**32 - 1 and block offsets with their high bit set are refused; a block's first and last positions must match its index record. The reader keeps its path absolute and checks on every read that the file is the one it opened, so a file replaced by a conversion raises instead of reading with a stale index. The default dtype of a read of mixed tracks is the narrowest type that holds every track exactly, float64 for a uint32 track read with a float32 one, which ``read_entries`` and ``figwig reorder`` relied on to round large integers. Sums into an integer dtype are taken in int64 and checked, where a uint8 sum of 200 and 100 was 44. Sums per label run a group's batches at a time with no copy of the output per thread, where 8 threads took 8 copies; a read uses one thread per 64 chunks it touches, keeps its pool between reads, and splits the pairs of a few chunks over the threads, so 64 windows read on one thread and 10,000 identical windows on all of them; a chunk that many windows fall on is decoded once into a scratch tile, where a million 1 bp windows over a megabase rescanned the tile per window; and a sparse read builds and frees its arrays one at a time, about 40 bytes per entry rather than 117.

	- Summaries, checksums and growing files. The index keeps each track's sum over every tile while those sums take at most 256 MB, and ``FigWigReader.tile_sums(tracks, chroms)`` gives them without decoding a chunk: a genome-wide profile at the tile's resolution, a per-chromosome total, or 1 Mb bins by a reshape, which is what a bigWig's zoom levels serve. Every chunk's CRC-32 is kept, and ``FigWigReader(path, verify=True)`` checks each chunk read against it, for uncompressed files, whose chunks had no checksum where a compressed chunk's zlib checksum is checked on every read. ``FigWigWriter(path, None, tracks, append=True)`` adds the tracks given to the file at the path in place, writing the new chunks, tables, index and last the header after its end, so that the cost is the new chunks and a writer that fails, or is killed, leaves the file readable as it was; ``FigWigWriter.add_file(path)`` adds every track of another file written with the same chromosomes, tile, level and order, copying its chunks; ``figwig merge -o all.fw a.fw b.fw`` does that from the command line; and ``figwig bw2fw --append`` adds bigWigs to a figwig file. The format's version is 3; a version 2 file, from this branch before these changes, is refused with a message that says so.

	- The bigWig reader takes a file whose index leaves lie in natural chromosome order, chr1, chr2, ..., chr10, where the ids run chr1, chr10, chr2, by sorting the leaves; two bigWigs of the test collection were refused as unsorted where pyBigWig read them.

	- Converters. ``BigWigReader.read`` and ``read_bigwig`` take ``keep_nan=``, with which an interval whose value is NaN reads as NaN rather than ``missing``, and ``figwig bw2fw`` uses it, so the NaN gaps of a Hi-C insulation or compartment track are NaN in the figwig file rather than 0; ``bw2fw --missing nan`` writes the bases no interval covers as NaN, for methylation and conservation tracks whose zeros are measurements; ``bw2fw -s`` is checked against every bigWig's chromosome lengths, so an hg19 bigWig with hg38 sizes is refused rather than converted with NaN tails, and the chromosomes the sizes file leaves out are named in a warning; ``fw2bw --missing`` writes the zeros of such a file back; ``figwig bam2fw`` writes its counts as entries on the ``-p`` threads, where encoding width-1 windows on the calling thread made it 2.4 times slower than ``figwig bam2bw``; and ``figwig reorder`` keeps the input's tile, groups and level.

	- How the chunks and the kernels are built for speed and size. A sparse chunk stores its offsets as varints with the bytes each track's take, so that a read of some of a group's tracks steps over the others', and a chunk whose nonzero values are all 1, as a tile of single-cell cut sites is, stores no values at all, with a ``one`` element type. Reads inflate chunks with libdeflate where the ``deflate`` package is installed, about twice as fast as zlib, choose each chunk's element type once rather than once per value, and cut their chunks into batches of 256; every kernel's inner loop runs over a one-dimensional row, which numba vectorizes where it does not vectorize the same loop over a two-dimensional array. The encoders count a tile's nonzero bases in one vectorized pass, then collect them with a branch per base when they are few and survey them without one when they are many; ``write`` copies a call's values only where it must; ``write_sparse`` sorts its entries once by one composite key; ``figwig bw2fw`` and ``bam2fw`` hand their arrays to the writer without a copy, and ``bw2fw`` reads each piece of a chromosome on a thread of its own while the piece before it is written.

	- After six user personas tried the format against bigWigs: ``FigWigReader.sums(chroms, starts, ends)`` sums intervals of any lengths, such as peaks or genes, which ``read`` with one ``width`` could not; ``figwig info`` prints what a file holds; ``bw2fw`` and ``fw2bw`` refuse to write over an output that exists unless ``-f`` is given, and ``-v`` prints a line per group and a summary rather than a line per chromosome; a reader keeps reading through an append in place and is told to open the file again once it has closed, since it holds the file by its inode and header rather than its size and modification time; a binned read on several threads summed a bin straddling two tiles from two threads at once and lost counts, and its batches are now not cut inside a window, with a copy of the output per thread only for a window longer than a batch may grow; a chunk whose damaged stream libdeflate rejected could be inflated by zlib short of its checksum and read as wrong values, and is refused; files are created with the mode the umask gives a new file rather than mkstemp's 0600; a writer dropped with work in flight no longer raises from its finalizer on a pool thread; ``select`` with a key no track has raises, naming the keys; an unknown chromosome's message names the file's chromosomes, a mismatched ``out`` says to pass ``dtype=``, a scalar start says to give one per window, a file ``add_file`` refuses says which chromosomes or which of order, tile and level differ, and a command's ``n_jobs`` error names ``-p``; a torch dtype is taken as the numpy one; an empty cell of a metadata table is no attribute; and the docs say which layout dense float tracks want, that ``bins`` is a width where pyBigWig's ``nBins`` is a count, that figwig's means count every base where pyBigWig's and deepTools' count covered ones, and that DataLoader workers do help.

	- After six more personas: ``FigWigReader.sums`` and ``read(bins=)`` take ``nan='skip'`` and ``nan='count'``, so a mean over the bases a track covers, as pyBigWig and deepTools give it, is the sums with 'skip' over those with 'count' on a file written with ``--missing nan``; a binned sum of a chunk that many windows do not fall on, or of more tracks than a scratch tile holds, is taken from the chunk's entries without a scratch tile, so ``sums`` over 3,000 cells is no longer refused and takes 1 s for 58,705 peaks where it took 73 s in halves; a batch of chunks encoded in several goes, as float64 chunks and large ``write_sparse`` batches are, was joined from the whole of each go's buffer rather than its streams, so a float64 track of two or more whole tiles in one call, or a large sparse batch, was written corrupt, and is not; a chunk stored as it is inside a compressed file had no checksum unless ``verify=True`` was given, and its CRC is now checked on every read, as are, in version 4 of the format, a CRC-32 of the tables and directory kept in the header and one per index record, so that a flipped chromosome length or run offset is refused rather than read by; a float32 sum is taken in float64; ``merge``, ``reorder`` and ``bam2fw`` refuse an existing output without ``-f`` (``--force`` for ``bam2fw``); ``fw2bw`` writes each bigWig beside its name and moves it into place when complete; ``figwig info`` survives a closed pipe and reports bytes past the end a killed append left; ``append=True`` with ``attributes=`` adds to the file's attributes; a missing input file, chromosome sizes file or table is a message rather than a traceback, Ctrl-C exits quietly, a space-separated table is told it needs tabs, ``merge`` names the first file in its messages, and ``reorder -v`` prints a summary; 16-bit float dtypes are refused with a message; and the docs give the compile times of every kind of first call, the layout that count tracks want (one group of many), the lossless round trip of signal tracks with explicit zeros through ``--missing nan``, and the scaled-region recipe.

Writing
-------

	- ``_zoom_records``, the kernel that summarizes items into one zoom level's records, holds the open record in locals and stores it back when it returns, instead of writing it to the level's state arrays for every item. Zoom levels are summarized on different threads at once, and their small state arrays can share a cache line, which makes the kernel many times slower in the processes where the arrays happen to be allocated next to each other. The files written are unchanged. Thanks @YaoxiangLi!


Version 0.1.0
=============

Reading
-------

	- Initial release. ``BigWigReader(path).read(chroms, starts, width, out=None, n_jobs=8, missing=0.0)`` reads the per-base values of many windows of one width into a float32 numpy array of shape ``(n, width)``, on up to ``n_jobs`` threads, or one per CPU with ``n_jobs=-1``. ``read_bigwig`` does the same in one call, and given a list of bigWigs reads them all into one array of shape ``(n, len(bigwigs), width)``, with every file's batches on one pool of threads.

	- The values are those pybigtools' ``values(chrom, start, end, missing=missing)`` gives: ``missing``, 0 unless given, where no interval covers a base or an interval's value is NaN, and NaN past the end of a chromosome. A window on a chromosome that the file does not have, which writers leave out when it has no data, is ``missing`` throughout, and a warning names the chromosomes.

	- bedGraph, varStep and fixedStep sections are read, compressed or not, including pyBigWig's fixedStep blocks whose index entries overlap by a few bases. A file or data block that figwig does not read, such as a bigBed, a big-endian bigWig, a corrupt or truncated index, or a block with overlapping intervals, raises a ``ValueError`` that says what it found.

	- A ``BigWigReader`` can be read from several threads at once and pickled, so it can be part of a PyTorch Dataset read by DataLoader workers under any start method.

	- The reader began inside tangermeme's ``extract_loci`` (tangermeme #107).

Writing
-------

	- ``write_bigwig(paths, chrom_sizes, chroms, starts, values, ends=None, missing=0.0)`` writes what ``read_bigwig`` reads: windows on any chromosomes, in any order, with values of shape ``(n, width)`` for one file, or ``(n, len(paths), width)`` for several, channel ``i`` to the ``i``-th file. With ``ends``, it writes intervals and one value for each. Bases and intervals whose value is ``missing`` or NaN are left out, so that reading with the same ``missing`` gives the values back, and bases past the end of a chromosome, which ``read_bigwig`` gives as NaN, are accepted there. ``BigWigWriter(path, chrom_sizes, zooms=10, level=6, engine='auto', n_jobs=8)`` writes the same values a batch at a time with ``write(chroms, starts, values, ends=None, missing=0.0)``, each call after the last. Values are converted and laid out about a million at a time, however many one call holds. Data blocks are compressed on up to ``n_jobs`` threads by zlib's ``compress2()``, or by libdeflate when the ``deflate`` package is installed (the new ``fast`` extra), both called without the GIL, except on Windows, where neither library can be loaded and Python's zlib module compresses the blocks; ``engine='isal'`` uses ISA-L. Zoom levels are built when the writer is closed.

	- Each window, or each 65,536 bases of a wider one, is written as whichever section type takes it in the fewest bytes: fixedStep for runs of bases, varStep for scattered bases, or bedGraph for stretches of one value. Intervals are written as bedGraph, as they are given.

	- Written files are laid out as libBigWig, pyBigWig's writer, lays them out, and a file of intervals, or of single bases as windows of width 1, written with ``missing=numpy.nan``, without zoom levels and with zlib at level 6, is pyBigWig's byte for byte. Where libBigWig writes a wrong value, figwig writes the correct one: the header's maximum when the first value is the largest or no value is positive, the end of the last fixedStep block of each call, which libBigWig puts 6 bases past it, and the sum and sum of squares of the last zoom record of each zoom block, which libBigWig leaves at 0. libBigWig's empty blocks are not written, and zoom levels go on past a level that is no smaller than the one before it, where libBigWig stops.

figwig bam2bw
-------------

	- ``figwig bam2bw``, a command, is bam2bw 0.5.1 with the same arguments, outputs and messages, reading files as the winner of a speed search over bam2bw's code reads them, a BAM file with libdeflate and a numba kernel on the ``-p`` threads and a BED/tsv file with a numba kernel, and writing the counts with ``BigWigWriter``, with libdeflate at level 1. Its bigWigs hold bam2bw's entries, but not its bytes, and ``-z`` writes figwig's zoom levels. ``-p`` is a number of cores: files are read one after another, each on every core, and files read on one thread (SAM, ``--mate_pairs``, remote files, gzipped BED/tsv files that are not BGZF) by a pool of processes alongside them. It needs the new ``bam2bw`` extra. A BAM file's keys, one per counted read end, are counted a group of chromosomes at a time while the file is read and then dropped, so that for a coordinate-sorted BAM the array that holds them is the size of its largest chromosome's rather than the whole file's.

Claude Code skill
-----------------

	- ``figwig install-skill`` installs figwig's Claude Code skill, which teaches a coding agent to read and write bigWigs with figwig and to convert reads with ``figwig bam2bw``: the signatures and shapes, the rules a write follows, the error messages and their causes, and the measured gain from threads. It copies the skill into ``~/.claude/skills/figwig``, or ``-d DIRECTORY/figwig``; ``--symlink`` links to the package's copy instead, and ``--force`` replaces an installed copy, which an upgrade of figwig needs to pick up a changed skill.

Platforms
---------

	- Tested on Linux with Python 3.10 to 3.14, and on macOS and Windows with Python 3.10 and 3.13. On Windows, which has no ``os.pread`` and where neither zlib's library nor libdeflate's functions can be loaded, blocks are read by seeking the file, and decompressed and compressed by Python's zlib module, with the same values. ``figwig bam2bw`` runs on Linux and macOS, since pysam does not support Windows.
